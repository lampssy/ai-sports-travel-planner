# Sprint 31 Design: Trip Context and Clarifying Search

## Summary

Sprint 31 reshapes search from a flat filter form into a structured ski-trip context flow. The free-text brief remains the primary input, but the app can ask a small number of high-impact clarification questions when important context is missing or ambiguous.

The goal is to make future travel effort, total-price, and stay-base work fit naturally without turning Snowcast into a generic AI travel planner.

## Product Boundary

Travel and budget context are recommendation constraints, not standalone itinerary-planning features. Snowcast should help users choose a better ski trip option; it should not build flights, train itineraries, transfer schedules, or full travel plans.

The "agentic" behavior in this sprint is structured and bounded:

- parse the user's trip brief into a trip context
- detect missing context that materially changes ranking
- show 1-3 clarification cards with concrete choices
- update filters and rerun search when the user answers

No open-ended chat surface is added in this sprint.

## Goals

- Introduce a durable trip-context model behind search.
- Keep the current search API and UI compatible while adding richer context incrementally.
- Add budget semantics that distinguish nightly lodging budget from approximate total-trip budget.
- Add clarification cards below the search input for missing or ambiguous high-impact fields.
- Keep deterministic ranking in control; LLM output can parse user text but must not decide ranking.
- Prepare the UI and data contracts for Sprint 32 car-first travel effort.

## Non-Goals

- No routing provider integration.
- No airport, train-station, transfer, or public-transport itinerary planning.
- No hotel-provider inventory or live accommodation prices.
- No fully conversational assistant.
- No hard requirement that every user answer every clarification before seeing results.

## Trip Context

Sprint 31 introduces a product-level trip context shape that can be projected into the existing `SearchFilters` contract.

Candidate fields:

- destination scope:
  - country/location
  - optional region or resort intent later
- traveler fit:
  - skill level
  - minimum quality tier
  - lift-distance preference
- travel window:
  - exact trip dates when known
  - month fallback when exact dates are unknown
  - derived trip duration when exact dates are known
- budget:
  - `budget_mode`: `lodging_nightly` or `total_trip`
  - lodging nightly min/max
  - total trip min/max when supplied
  - party size, defaulting conservatively when absent
- travel origin:
  - optional origin text captured for future travel effort
  - not routed or scored until Sprint 32

The current `min_price` and `max_price` continue to mean nightly stay-base budget. Total-trip budget is a new semantic layer and should not silently replace nightly lodging budget.

## Clarification Policy

Clarifications are generated by deterministic policy, not by free-form LLM reasoning.

Each clarification has:

- stable id
- question
- 2-4 answer options
- optional free-form answer affordance
- field patch applied to trip context
- short reason used for debugging and tests
- priority

Initial clarification types:

- Budget ambiguity:
  - Trigger when the user mentions a budget but the app cannot tell whether it is nightly lodging or total trip budget.
  - Example answers: `Nightly lodging`, `Total trip`.
- Missing duration:
  - Trigger when total-trip budget is supplied but neither exact dates nor duration are known.
  - Example answers: `3-4 nights`, `1 week`, `I will add exact dates`.
- Missing party size:
  - Trigger when total-trip budget is supplied and party size is unknown.
  - Example answers: `Solo`, `2 people`, `Family/group`.
- Missing origin:
  - Trigger when the user mentions travel effort, drive time, distance, "near me", "not too far", or total-trip budget with travel included.
  - In Sprint 31 this captures intent only; Sprint 32 makes it actionable.

Clarifications should not block search unless the selected budget mode cannot be interpreted safely. In most cases, search should run with available context and show which assumptions were used.

## UX

The existing free-text brief remains the first interaction.

After parsing:

- Keep showing "What we understood."
- Show applied context chips.
- Show up to three clarification cards below the input when useful.
- Each card offers concrete choices that update context immediately.
- The advanced panel remains available but should gradually become a context editor, not the primary interaction.

Examples:

- "Is EUR 1,500 your lodging budget or total trip budget?"
- "How long is the trip?"
- "Where will you start from? This will help estimate drive effort later."

The UI should avoid generic assistant language. The wording should stay ski-planning-specific.

## Ranking And Price Semantics

Sprint 31 keeps existing ranking behavior stable for nightly lodging budget.

When total-trip budget is selected, Sprint 31 may produce an approximate estimate using known reviewed facts:

- lodging estimate from stay-base nightly price and trip duration
- lift-pass examples when available
- rental example when available

Travel cost is not included until Sprint 32. If total-trip budget is used before travel origin is known, the UI should say travel cost is not included yet.

Total-trip estimates must be shown as approximate ranges, not precise quotes.

## Data And API Shape

Preferred implementation direction:

- Add internal trip-context models and mapping helpers.
- Extend parse output with structured context plus clarifications.
- Keep `/api/search` backward compatible.
- Add optional query parameters only when needed by the UI.
- Keep persisted current-trip changes out of scope unless required for compatibility.

The detailed implementation plan should decide whether clarifications are returned by `/api/parse-query` or by a new context endpoint. The decision should favor small API changes and frontend simplicity.

## Error Handling

- LLM parser failures fall back to the existing heuristic path.
- Clarification policy must still run on heuristic output where possible.
- Invalid context patches from the UI are rejected with field-level errors.
- Missing total-trip assumptions should produce explicit UI caveats rather than hidden defaults.

## Testing

Focus tests on deterministic behavior:

- trip-context validation
- budget-mode mapping
- clarification triggers and ordering
- parse-output compatibility
- search compatibility for existing clients
- frontend tests for clarification cards and context chip updates

LLM tests should continue to mock provider output and validate structure, not exact wording.

## Acceptance Criteria

- Existing search flows still work without answering clarifications.
- A user can enter an ambiguous budget and choose whether it is nightly lodging or total trip budget.
- A user can provide or answer duration/party-size context where total-trip budget needs it.
- The app can capture origin intent without doing routing yet.
- Search results and explanations remain grounded in deterministic ranking.
- Documentation explains that Sprint 31 adds bounded clarification, not generic chat.
